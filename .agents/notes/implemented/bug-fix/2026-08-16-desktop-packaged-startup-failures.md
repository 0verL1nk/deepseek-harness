# Agent Note: Desktop packaged startup failures — peer closure, src pruning, HMR internals

Status: implemented

English | [中文](2026-08-16-desktop-packaged-startup-failures.zh.md)

## Problem

The desktop release shipped as `dsh-v0.1.0-rc.5`, before the desktop moved to its own `v*` tag namespace, could not start on any machine: the packaged backend exited before readiness and the window showed only "DeepSeek Harness could not start". Reproduction against the shipped `app.asar` (forking `lib/backend.js` under `ELECTRON_RUN_AS_NODE`) exposed four independent defects, each invisible to the release workflow because nothing ever booted a packaged build. First, electron-builder prunes `node_modules` along the dependency graph it can walk, and harness packages reference each other through `peerDependencies`; nineteen packages reachable only over peer edges — including the Linux-only bash stack (`cordis-plugin-group`, `dsh-shell`, `dsh-fs`, `dsh-bash-local`, `dsh-compaction`, `dsh-workflow`, `dsh-invariants`, and the rest of the declared closure) — were absent from the archive. Second, the `files` negation `!node_modules/**/src/**` — meant to drop workspace TypeScript sources — also deleted npm packages whose built output lives under `src/` (`koffi`, every `@opentelemetry` CJS tree under `build/src`). Third, the profile boot's watch-only HMR instance requires Node loader internals; plain-Node `dsh` processes obtain them through the `node-addon-require-builtin` native fallback, which cannot read Electron's V8 realm layout, so the backend fork failed with "--expose-internals is required for HMR service" after the web host had already bound its port. Fourth, the profile module fallback symlinks every installation package into `$DSH_HOME/profiles/node_modules`, and in the packaged app those symlinks pointed into the `app.asar` archive — symlink traversal happens in the kernel, below Electron's archive interception, so every loader entry import resolved from the profile directory failed.

## Decision

The desktop package declares the peer-only runtime closure as direct `dependencies`, so every module the packaged backend resolves survives pruning regardless of the edge type it was reached over. The `files` negation is scoped to `!node_modules/@deepseek-ai/*/src/**`, keeping npm packages' `src/`-shaped output intact. `startBackend` forks with `execArgv: ['--expose-internals']`, which the vendored loader accepts as its internals source and which the native addon cannot provide under Electron. Two gates make the class regress-loud instead of regress-silent: `pnpm --filter @deepseek-ai/dsh-desktop run boot-smoke` forks the packaged backend exactly as the Electron main process does and requires the readiness handshake, and the [Desktop workflow](../../../../.github/workflows/desktop.yml) runs it on every pull-request check and on each platform's release build before artifacts are published. The desktop archive unpacks `node_modules` (`asarUnpack`), and `healProfilesModuleFallback` redirects a link target inside an `app.asar` archive to its `app.asar.unpacked` twin when one exists, so the fallback links always name real directories the kernel can traverse. The backend startup failure message now flattens `AggregateError` sub-errors through the `cause` chain (top five, with an elision count) so a broken composition stops presenting as an unexplained blank. Release channel policy: every `v*` tag publishes as a regular release — this distribution has one stable channel, so prerelease marking only hid releases from installed clients.

## Alternatives considered

**Bundle the whole runtime with tsdown (external only `electron`).** Rejected: the cordis Loader imports plugin entries by package name at runtime from the composed profile, so a static bundle cannot express the composition; native modules and `electron-updater` would still need unpacked `node_modules` handling.

**Generate the closure list from the composition files.** Rejected as the primary mechanism: the runtime set also depends on dynamic mounts inside `profile-boot` (timer, watch-only HMR) and on every future plugin's own peer edges, none of which a static generator can see. The boot smoke observes the real composition, which is the invariant that matters; the declared list is the fix, not the detector.

**Suppress the watch-only HMR mount for the desktop surface.** Rejected: it would silently break the documented live `cordis.patch.yml` reload contract for desktop users; passing the flag costs nothing and keeps the surface on the same path as every other `dsh` host.

## Consequences

Adding a plugin to the web composition that peers on a package outside the desktop dependency list no longer produces an uninstallable release — the boot smoke fails the Desktop workflow first, and the fix is again one declared dependency. Packaged archives keep some workspace `src/` byte weight they cannot shed without a narrower rule, and the desktop manifest now carries a dependency list that mirrors the composed profile rather than what the shell itself imports; the README states that contract. The single-channel policy means a genuinely broken tag cannot be withheld from updater clients by marking it prerelease — a broken release must be superseded by a fixed one, as the first desktop-versioned release supersedes it.
